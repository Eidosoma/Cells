# Amendment 1, 25 November 2026: eight clarifications of the contract

**Written by the registration's author from the lead's rulings, after Part 1's criteria tag (`ensemble-reexpression-criteria-part1-2026-11-25`, 77680d9e) and before any registered run.**
- **Where it comes from.** The Part 1 builder, who reads `SPEC.md`, `READOUTS.md`, `TABLE.md` and `inputs.json` only, asked. The lead answered, and the builder works to the answers. The lead then answered this author's questions on a first text of this file (9149f2a4), and those answers are in it.
- **What changes.** The contract's words alone. No number, scale, band, class, window, threshold or count changes, no plant's change or named entry does, and no data file. EP2 gains one way to be unscorable (item 7), which can only make its consumer inconclusive. **One check is weaker, and the lead accepts it** (item 6).
- **Value-silent.** It holds no number of a run of either side.
- **Precedence.** Where this amendment and an earlier file of this folder differ, it governs. Every other sentence stands.

Each item quotes the sentence that it replaces or adds to, as it stands at the tag, and says where.

## 1. A pool restart resumes a first leg's checkpoint

**Replaces, for a pool restart alone,** in `SPEC.md` §4:

> **A restart** (a support run) resumes a checkpoint of its judged run at the checkpoint's time.

**Now:** a pool restart resumes a checkpoint that a first leg of the same definition and seed wrote, through a file, at the restart's time. A live pool writes a checkpoint at the end of a leg only. The resumed leg is compared with the judged (uninterrupted) run, as the spec says (`CRITERIA.md` §4.1).

**The first leg** is recorded in the support run's own record: its command, its checkpoint file and the checkpoint's sha256. It is not a registered run and has no table entry, so it owns no entry. The two pool restarts submit the composed file and use the same function as a pool run (item 8).

**Replaces, for a pool restart alone,** in `CRITERIA.md` §5:

> A restart's E entry belongs to the judged run it resumes, never to the support run.

**Now:** a pool restart's E entry belongs to the judged run it is compared with, never to the support run. The owner is the same run as before.

**Unchanged:** an ionic restart resumes a checkpoint of its judged run. What the checker confirms from the run's own record (`CRITERIA.md` §4.1) stands.

## 6. The rehearsal's off-grid run

**Adds to** `SPEC.md` §8:

> one run whose declared change is off the grid (the reason `off_grid_change`),

**Now also:** the rehearsal's off-grid run is made by an explicit switch of the run driver, which is recorded in the run's record as a flag. Without the switch it is refused before any run, and the driver's refusal has kind `harness` (`TABLE.md` §4). A registered run made with the switch on is refused (kind `harness`). The rehearsal's one named run is the only lawful use.

**"Off the grid" is `SPEC.md` §4's rule and no other:** a change is on the grid if it differs from some k h by at most 2 ε t. So the change of `integrated` at 0.015 s is on the grid, and the driver does not refuse it. In `cell` and `base` the changes are the pool's events, which split steps by design, and this item says nothing of them.

**What is weaker, and accepted by the lead.** At the tag, a run with an off-grid change ran, was refused with the reason `off_grid_change`, and its readouts were judged. A run that the driver refuses has no rows, so nothing of it is judged. The definitions of the registered runs are checked on the grid before any run.

**Unchanged:** the judge's own rule, in `SPEC.md` §4:

> A run whose step list splits at one has more accepted steps than end_s/step_s, and it is refused with the reason `off_grid_change` (`CRITERIA.md` §5).

## 8. What a registered pool run submits, and where an ionic run's schedule comes from

**Adds to** `SPEC.md` §3.2:

> For each seed and each cell's pool, the live assembly pool runs the block's definition to its `end_time_s`.

**Now also:** a registered pool run submits the composed file (the one at the world's first step, h₁) and runs its pools by the function that `cells assembly-pool resolve` uses. No part of the exporter compares it with an ionic run's own resolution.

**Replaces,** in `SPEC.md` §3.3:

> It makes the schedule from the pool run of the same seed, world and cell.

**Now:** an ionic run's schedule comes from its own resolution of the composed file's pools.

**Replaces,** in `TABLE.md` §3, `inputs.assembly`, the sentence that item 7 quotes.

**Now:** `pool_seeds`: cell ID to integer, the seeds of the composed file's pools, by position (class E, `CRITERIA.md` §4.1).

**What joins the two.** The registered pool run is a separate run of the same pools. The 19 arrays, the event path and the seed are class E of that run, as before (`CRITERIA.md` §4.1), and no array or event of an ionic run's own resolution is an entry. An ionic run's switch list and its channel schedule are the class E entries that join it to the captured path.

**Adds to** `TABLE.md` §3, the row `declared_strings`:

> list of strings, sorted: **every** registered string that the definition the engine parsed and ran declares (its model, laws, operators, kinds, solver, field solver and observable), one each.

**Now also:** a pool run's `strings` are the pool's own only: its model, its topology and its observable, and what the pool's parser declares. The ionic definition's are not among them. Its `declared_strings` are the same set.

**Replaces, for the `channel` and the `stream_id` of a pool run alone,** in `TABLE.md` §3, the row `inputs`, the sentence that item 3 quotes.

**Now:** `channel` and `stream_id` of its `inputs` are read back from that file.

**Unchanged:** `seed` and `pool` of its `inputs` are read back from the definition the engine parsed and ran.
