# Amendment 1, 25 November 2026: eight clarifications of the contract

**Written by the registration's author from the lead's rulings, after Part 1's criteria tag (`ensemble-reexpression-criteria-part1-2026-11-25`, 77680d9e) and before any registered run.**
- **Where it comes from.** The Part 1 builder, who reads `SPEC.md`, `READOUTS.md`, `TABLE.md` and `inputs.json` only, asked. The lead answered, and the builder works to the answers.
- **What changes.** The contract's words alone. No number, scale, band, class, window, threshold, plant or count changes, and no data file.
- **Value-silent.** It holds no number of a run of either side.
- **Precedence.** Where this amendment and an earlier file of this folder differ, it governs. Every other sentence stands.

Each item quotes the sentence that it replaces or adds to, as it stands at the tag, and says where.

## 1. A pool restart resumes a first leg's checkpoint

**Replaces, for a pool restart alone,** in `SPEC.md` §4:

> **A restart** (a support run) resumes a checkpoint of its judged run at the checkpoint's time.

**Now:** a pool restart resumes a checkpoint that a first leg of the same definition and seed wrote, through a file, at the restart's time. A live pool writes a checkpoint at the end of a leg only. The resumed leg is compared with the judged (uninterrupted) run, as the spec says (`CRITERIA.md` §4.1).

**Replaces, for a pool restart alone,** in `CRITERIA.md` §5:

> A restart's E entry belongs to the judged run it resumes, never to the support run.

**Now:** a pool restart's E entry belongs to the judged run it is compared with, never to the support run. The owner is the same run as before.

**Unchanged:** an ionic restart resumes a checkpoint of its judged run. What the checker confirms (`CRITERIA.md` §4.1) stands. The first leg is not a registered run (`inputs.json` does not list it), and it owns no entry.

## 2. `restart.step_index` of a pool restart

**Adds to** `TABLE.md` §3, the row `restart`:

> null, or `{"time_s", "step_index", "through"}`: the checkpoint's time, its step index and how it was saved (through a file)

**Now also:** `restart.step_index` is null for a pool restart, since a pool has no steps. It joins the places where null may stand, which the same section limits:

> `null` stands only where this table says so.

## 3. A pool's `stream_id`

**Adds to** `SPEC.md` §2.5:

> Its `inputs` hold, per cell, the pool block with its `channel`, its `stream_id` and its `seed` (class E, §2.4), which is `seeds[k]`:

**Replaces, for `stream_id` alone,** in `TABLE.md` §3, the row `inputs`:

> the world's block, read back from **the definition the engine parsed and ran**, never a copy of this folder.

**Now:** the `stream_id` of a pool is its position in the composed file (first pool 0), read back from that file. A pool definition of the live engine has no such field.

**Unchanged:** it is compared as an echo with `inputs.json`'s. `seeds[k]` is the captured seed of that pool as it stands, and nothing is added to it for the position.

## 4. `declared_change` in the rehearsal's inputs

**Adds to** `SPEC.md` §8:

> `inputs_rehearsal.json` has `inputs.json`'s schema (with `p`, `amount_refs`, `closure_terms_V` and `scales` in every world), with its own worlds and runs, named `inv_<name>`,

**Now also:** a run's entry in `inputs_rehearsal.json` may carry `declared_change`: a list of `{"path": [...], "value": ...}` over the world's block, and `{"exchange_channels": [cell, cell]}` for a composed file. In the registered `inputs.json` the two plant runs are EP1 and EP2 by their `variant`, as `PLANTS.md` says.

**Adds to** `README.md`, the rules for every reader:

> **The exporter's builder receives `TABLE.md`, `READOUTS.md`, `SPEC.md` and `inputs.json`.**

**Now also:** the builder was told the declared changes of EP1 and EP2, and nothing else of `PLANTS.md`.

## 5. The rehearsal's `p` names its integrator

**Adds to** `SPEC.md` §8:

> one family on the engine's IMEX integrator, with **`p` = 2 in its world's block**, at steps where its order is resolved.

**Now also:** `p` = 2 is ARS(2,2,2), label `imex`. `p` = 4 is RK4, label `rk4`. Any other `p` is refused by name.

**Adds to** `TABLE.md` §5, whose list of labels begins:

> "labels": {"inner_model": "", "rk4": "", "field_solver": "", "field_solver_floor": "", "closure": "", "constant_field": "", "kv15_mh": "",

**Now also:** the rehearsal's strings note holds the label `imex` beside them. Every registered world of Part 1 has `p` = 4, so the registered note needs no such label for Part 1.

**Unchanged:** `p` is the declared order of the candidate.

## 6. The rehearsal's off-grid run

**Adds to** `SPEC.md` §8:

> one run whose declared change is off the grid (the reason `off_grid_change`),

**Now also:** the rehearsal's off-grid run is made by an explicit switch of the run driver, recorded. Without the switch it is refused before any run.

**"Off the grid" is `SPEC.md` §4's rule and no other:** a change is on the grid if it differs from some k h by at most 2 ε t. So the change of `integrated` at 0.015 s is on the grid, and the driver does not refuse it. In `cell` and `base` the changes are the pool's events, which split steps by design, and this item says nothing of them.

**Unchanged:** the judge's own rule, in `SPEC.md` §4:

> A run whose step list splits at one has more accepted steps than end_s/step_s, and it is refused with the reason `off_grid_change` (`CRITERIA.md` §5).

## 7. EP2's `pool_seeds`

**Adds to** `TABLE.md` §3, `inputs.assembly`:

> `pool_seeds`: cell ID to integer, the seeds of the pool run the file was composed from (class E, `CRITERIA.md` §4.1);

**Now also:** EP2's `pool_seeds` are by the pool's position in the composed file, so they are its honest run's. Its schedules, its switch list and its `controls.channel` are the swapped ones, as `PLANTS.md` says.

## 8. What a registered pool run submits

**Adds to** `SPEC.md` §3.2:

> For each seed and each cell's pool, the live assembly pool runs the block's definition to its `end_time_s`.

**Now also:** a registered pool run submits the composed file (the one at the world's first step) and runs its pools by the function that `cells assembly-pool resolve` uses. No part of the exporter compares it with an ionic run's own resolution.

**Replaces, for the `channel` and the `stream_id` of a pool run alone,** in `TABLE.md` §3, the row `inputs`, the sentence that item 3 quotes.

**Now:** `channel` and `stream_id` of its `inputs` are read back from that file.

**Unchanged:** `seed` and `pool` of its `inputs` are read back from the definition the engine parsed and ran. A pool run's path, an ionic run's switch list, its channel schedule and its `pool_seeds` are each class E, as before (`CRITERIA.md` §4.1).
