## 1. T4's class R takes no accuracy (J01)

**The gap.** CRITERIA §3.2 (L59) adds the reference's accuracy to every entry of READOUTS §3's R column, and T4's
default heat is one of them (READOUTS §3, L41); READOUTS §3 defines R so (L51). CRITERIA §3.4 (L82) writes T4's class R
as |H_face(h) − H_def(h)| ≤ e_round, with none.

**The ruling.** §3.4's formula governs T4's class R: it takes no accuracy. Every other class-R entry takes it (§3.2), and
class B takes none (§3.3, L73; §3.4, L83).

**Can a verdict depend on it?** In principle, at an entry within H_def's accuracy of its bound, which C0 holds to 10⁻³⁸
of s_F (R8, L190).

**Does it make a pass easier, or soften a fail?** Neither: it removes that accuracy from T4's tolerance.

## 2. A duplicate key, in a table or in another file the judge reads (J03, its third clause)

**The gap.** C16 (amendment 5, L213) refuses a file with a duplicate key, and does not say what of it is judged, nor what
follows for a file that is not a table.

**The ruling.**
- **A table** with a duplicate key is refused as a table whose hash departs is (TABLE §1, L12–13): every run in it is
  refused, and every entry that can be formed from it is judged, a fail standing (CRITERIA §4, L160–161). An entry that a
  repeated key reaches is formed from each of the key's occurrences; where two keys repeat on one entry, from every
  combination of their occurrences. A fail in any stands.
- **Every other file the judge reads** is read the same way: a duplicate key in the strings note (amendment 5's L3), the
  map (L1) or a reference file refuses that file, as C16 refuses a table. A refused strings note or map refuses every run
  or pair that it binds, and their readouts and digests are still judged, a fail standing; a note's fault found before any
  table is hashed is corrected by a dated second note (L3, L324–325). A refused reference is item 17's.

**Not taken: the judge's reading** (J03), that nothing of such a table is judged. It would add a second place where a fail
goes unseen, which CRITERIA §4 (L180) does not hold.

**Can a verdict depend on it?** Yes.

**Does it make a pass easier, or soften a fail?** Neither: a refused run or pair cannot pass, and every fail that can be
formed stands.

## 3. A table that is a format sample (J03, its fourth clause)

**The gap.** TABLE §4 (L99–100) refuses in judgement a table whose sha256 is the sample's, and does not say whether its
readouts are judged.

**The ruling.** A table whose sha256 is a line of either of item 9's notes refuses every run in it, and nothing of it is
judged: its numbers are the sample's, on which no tolerance, scale or verdict may depend (TABLE §4, L98–99). CRITERIA
§4's "one place" (L180) is read with it.

**Can a verdict depend on it?** Yes: its runs are refused, and their arm is at best inconclusive.

**Does it make a pass easier, or soften a fail?** Neither. A fail formed from a sample's numbers would be no run's.

## 5. The echo of `inputs`, key for key (J06)

**The gap.** TABLE's opening (L6) allows and ignores extra keys, and TABLE §3 (L46) makes `inputs` the world's block,
read back from the definition the engine parsed. Read into the echo, the opening lets a key that the block lacks, which
may carry physics, pass unseen. D6 (amendment 5, L230–231) reads the opening for series. A run refused at parse has no
parsed definition, and V2 (L36) gives it the submitted declaration as its `inputs`, whose keys are the engine's and not
the block's.

**The ruling.**
- **The opening does not reach inside `inputs`.** At every level the echo holds exactly the keys of its world's block in
  `inputs.json`, without `outputs_s` and `compare_s`, with `step_s` (TABLE §3, L46). A key that the block lacks, or one
  that it holds and the echo lacks, is a departing echo (CRITERIA §4's first row): the run is refused, and nothing of it
  is judged.
- **Lists** compare in order, but links and faces, which R1 (L183) makes sets.
- **Two forms stand:** arm 7's `{}` (amendment 4 item 1, L23), whose departure is item 8's, and the no-router runs' (item
  3, L73–74).
- **A run refused at parse** echoes, in `inputs`, its world's block as registered: `inputs.json`'s block, with the run's
  `step_s` added and `end_s` a number (TABLE §3, L46), key for key as above, and never the engine's raw definition. Its
  `definition` is the declaration submitted (V2, L36), and the checker confirms that the declaration is the block's (the
  protocol's §3, L78). This replaces V2's "the submitted declaration" for `inputs`.
- **D6 stands:** extra series are allowed and recorded, and the opening holds everywhere outside `inputs`.

**Can a verdict depend on it?** Yes: a departing echo refuses its run, and the expected refusal's echo is judged by it.

**Does it make a pass easier, or soften a fail?** It makes no pass easier: it removes a pass on an echo that holds a key
its world lacks. It can leave a fail unseen only as CRITERIA §4's departing echo does (L180–181), on a run that is not the
registered world, and that sentence's "one place" is read with it.

## 6. The accuracy in τ (J13)

**The gap.** CRITERIA §3.5 (L94) writes τ = 3 est + accuracy + e_round(last compared time), and names no time for the
accuracy, which the reference gives at each compared time.

**The ruling.** τ takes the smallest of the reference's accuracies over the compared times.

**Not taken: the judge's reading** (J13), the accuracy at the last compared time, where C5 (L202) takes e_round. That is
larger where an earlier time's is smaller, by at most R8's bound for an accuracy (L190): 10⁻³⁸ of the scale for a
propagator or closed form, and 10⁻¹² for an integral, which arm 5's and arm 6's class-S heats are. The judge's reason
gave 10⁻³⁸ alone.

**Can a verdict depend on it?** Only at an entry within that bound of τ.

**Does it make a pass easier, or soften a fail?** Neither. **Disclosure:** with the smallest, the reference's own error at
the time of the largest difference may exceed the accuracy taken, by at most the same bound.

**Does it make a pass easier, or soften a fail?** Neither.

## 8. Arm 7: what binds a pair, and what a refused pair leaves judged (J23)

**The gap.** CRITERIA §3.8 (L152–154), amendment 4 item 1 (L23–28), V5 (L102–105), R6 (L188), R7 (L189) and L1
(L291–293) refuse a pair whose `definition` is missing, whose wash-side hash is not the strings note's, whose shared parts
hash apart, whose pointer is empty or does not resolve, whose `operators` depart from the note, or whose two sides differ
where they must be equal. None says what of a refused pair is judged, and V5's "all six differ" (L102–103) names no
consequence.

**The ruling.**
- **What binds a pair.** A pair is bound where its wash side's `definition` is present and hashes, in L1's canonical form,
  to the strings note's hash for that pair (V5, L102–103). A bound pair's digests are compared whatever else departs.
- **Refused, and judged.** Each of these refuses the pair, and every digest that can be compared still is, a fail standing
  (CRITERIA §4, L160–161):
  - a `definition` that the exporter omitted, on either side;
  - the two sides' shared parts hashing apart (V5, L103–104);
  - a pointer that is empty or does not resolve (L1, L291–293);
  - `operators` that depart from the note, or that do not differ by the wash on one side and the router on the other
    (R6, L188; CRITERIA §3.8, L152–153);
  - `t`, `solver`, `heat` or `heat_id` that differ between the sides (amendment 4 item 1, L24; R6, L188), or `world`,
    `variant`, `step_s` or `steps` (R7, L189);
  - an `inputs` other than `{}` (amendment 4 item 1, L23);
  - two pairs whose wash sides hash alike: both are refused, since all six differ (V5, L102–103).
- **The rule on operators, and its consequence.** In arm 7, R6 compares `operators` exactly with the note, and a departure
  refuses the pair (L188). It does not make the pair a departing echo, as it makes a run of arms 1 to 6. So a bound pair
  whose operators depart is refused, and its digests are still compared, a fail standing.
- **Not bound.** A pair whose wash side's `definition` is present and hashes to another value than the note's is arm 7's
  departing echo: it is not the registered pair, so it is refused and nothing of it is judged (CRITERIA §4's first row,
  L165).
- **A map that departs from L1 or V5** stays as the reading note's J24 has it: the pair is refused, and every digest that
  can be compared is.

**Not taken: the judge's reading** (J23), and this amendment's first form of this item, that each of these failures is a
departing echo with nothing judged. Under them a pointer fault in the builder's map, or a `definition` that the exporter
omitted, would leave a bound pair's digest fail unseen, against the note's J24.

**Can a verdict depend on it?** Yes: arm 7, and so FR-57's takeover line.

**Does it make a pass easier, or soften a fail?** No pass: a refused pair cannot pass (CRITERIA §4, L176). It can leave a
difference of digests unseen only in a pair that is not bound, whose wash side hashes to another world than the
registered pair's, where a difference is no evidence about the registered pair. CRITERIA §4's "one place" (L180) is read
with that case alone.

```json
{"entries": [{"entry": "<run>|<readout>|<class>", "rests_on": "<run>|<readout>|<class>"}]}
```

- **An entry with no such citation,** one whose cited miss the rehearsal's record does not hold, or one whose readout or

- **A name that is not an arm 6 entry** is recorded, and changes nothing: phase 1 is never re-scored. With no such file,

**Not taken:** this amendment's first form of this item, `{"entries": ["<run>|<readout>|<class>"]}`, under which an entry

**Can a verdict depend on it?** Yes: arm 6, and so FR-57's third line.

**Does it make a pass easier, or soften a fail?** No pass: arm 6 is then at best inconclusive. It sets aside only an entry

## 14. A ledger's error, under V5's marks (G14)

**The gap.** V5 (L97–99) marks each `wash_only` entry `record`: true "for an amount, a heat, a free energy or that
magnitude, and false for everything else", and lets at most one be true, the magnitude's. The wash saves its own ledger's
error beside its records (amendment 5's disclosures, L438–439), and builder B's digests add arrays for the ledgers (its
G14). Whether an array of a ledger's error is "an amount" is not said: the words that amendment 5's fifth answers
replaced had it false (L421), and the words that replaced them do not say. Nor does V5 say what follows where the checker
finds a mark wrong.

**The ruling.** An array of a ledger's error is an amount under V5's marks, whatever its ledger's unit (CRITERIA §3.7,
L122–123: fmol, pJ or C), and is marked true. Since at most one entry is true, the magnitude's, it cannot stand in
`wash_only`: it is mapped to the router's array of the same meaning, as a meaning the builder adds (V5, L89), and compared
bit for bit (L1), or its pair is refused (V5, L99).
- **The judge** sees only the marks: it refuses a pair whose `wash_only` is otherwise (V5, L99).
- **The checker** confirms every mark (V5, L99–100). An array of a ledger's error that the checker finds unmapped or
  mis-marked refuses its pair, and every digest fail that can be formed stands (CRITERIA §4, L160–161).

**Why this reading.** It is the one under which such an array, departing, can still fail its pair. Mapped, its digest
must equal the router's, and a difference fails arm 7's criterion E (CRITERIA §3.8). Marked false, it would stand in
`wash_only` with no limit and be compared with nothing, so that no departure of it could be seen.

**Can a verdict depend on it?** Yes: arm 7, and so FR-57's takeover line. A pair whose wash saves such an array, with no
router array of its meaning, is refused.

**Does it make a pass easier, or soften a fail?** Neither: it removes an exemption.

## 15. What counts as invented (the lead's ruling)

**The gap.** TABLE §4 runs the format sample on invented worlds, "none of `inputs.json`'s volumes, flows, times or
concentrations" (L86–87), and the protocol's §3 has the builder run no registered world before the run tag: "parse
checks, unit rows and invented worlds only" (L75). A rescaled copy of a registered world meets the first's letter, and
is the registered world.

**The ruling.** A world that the format sample's runs or the builder's smokes use (the protocol's §5, step 6, L111–114)
is invented only where:
- its volumes, flows, times and concentrations are its own, none of this folder's (SPEC §8, L210–212; TABLE §4,
  L86–87); and
- it differs from every registered world by a factor of at least 2 in one dimensionless group that the outputs depend
  on, or by its network. **The groups** are those that the world's closed forms in LAWS take: among them z = kh and the
  level ratio c₁/c₂ (§1, §2), an exchange's f and x/c (§3), a residence time's Qt/V and the ratio of volumes (§4), a
  portion's v/V and x/c (§6), a face's PA/Q beside a flow (§8), and the throughput ρ (SPEC §1). A rescaled copy counts as
  the registered world.

The groups that a refusal depends on may keep their registered values, so that a smoke finds a step the engine refuses
(L113–114).

**Can a verdict depend on it?** No. It binds what the builder may run before the registration tag.

**Does it make a pass easier, or soften a fail?** Neither: it narrows what counts as invented.

## 16. A refusal at run time, and an error that nothing names (G26, G30)

**The gap.** TABLE §3's kinds (L68–76) give `domain` to a refusal "by name" of a value outside a declared domain, at parse
or at run time (L73), `check` to the engine's own energy, material or charge check (L75), and `harness` to anything the
engine did not raise, "a crash" among them (L76). The exporter sets the kind "from what the engine raised" (L68–69).
SPEC §1 has the router refuse "by name, at parse for every declared segment and at run time where a schedule changes Q"
(L68–69), and a default-heat exchange outside its domain "refused by name" (L92–94). At run time, though, a refusal
surfaces as the runner's numerical error, which carries no name (builder B's G30), and an error that nothing names is
placed by none of the kinds. Builder B's first reading made it `domain`, recorded as unnamed (its G26).

**The ruling.**
- **Naming at run time.** The driver names a run-time error by the engine's own host-side refusal conditions, run on the
  refused step's start state: the router's (`refusal_condition`), and in a world with sites the site operator's
  (`site_occupancy`'s). A name found so is the engine's own, since those functions are engine code (after FR-45's
  precedent, as the lead relays it), and the kind is `domain`.
- **Their order.** Every condition that applies is run, whatever an earlier one found, and the message records every name
  found, in the order run, the router's first. The kind does not depend on the order: it is `domain` where any names the
  error.
- **An error that nothing names** is `harness`, recorded as unnamed, with the engine's message as raised (L53). It is not
  `domain`, which needs a name (L73), nor `check`, which needs the engine's own check, whose residual above its tolerance
  is the evidence (L75; CRITERIA §3.7, L118–124; the protocol's §7).
- **Every run-time case of `domain`** (TABLE §3, L73) has its naming condition listed in the exporter's README. A
  throughput above its bound where a schedule changes Q is the router's. A default-heat exchange outside its domain, χ
  with kh (the protocol's §11, L297–298), is named by the router's `refusal_condition` too, as builder A's forms give it
  (the lead's relay). A case that no condition names stays `harness`. At the exchange's boundary the registration judges
  nothing (SPEC §1, L94).
- **The exporter's README** lists this mapping, and the checker confirms it (L68–69).

**Why this is the strict fill.** As `domain`, an unnamed failure would satisfy the expected refusal, `F6 h=4.0 refused`,
which must be refused with kind `domain` (CRITERIA §3.7, L137–138); as `harness` it is refused another way, and arm 3 is
at best inconclusive (L139–140). As `check` it would be a stop with no evidence, whose message could not meet M1. Running
every condition, and recording every name, leaves no refusal named by one condition and hidden by another.

**Can a verdict depend on it?** Yes: arm 3, through its expected refusal. Elsewhere `domain` and `harness` refuse alike
(CRITERIA §4, L169), and no verdict reads a refusal's name.

**Does it make a pass easier, or soften a fail?** Neither: it removes a way for an unnamed failure to pass for the expected
refusal.

## 17. A reference that C0 refuses

**The gap.** CRITERIA §4 (L182–184) has C0 read each reference file before any engine run is read, and "A fault is named
and refused". It does not say what follows for the arm whose reference is refused.

**The ruling.** An arm whose reference C0 refuses is not judged: the judge runs C0 on the references and then opens the
tables (amendment 5 C15, L212), and an arm whose reference it refuses has none of its tables' entries formed. The arm,
and its request's line, are then at best inconclusive (amendment 4 item 1, L19–20: nothing passes empty). C0's remedy
comes before any run: the lead's C0 dry run on the tagged references names any fault (the protocol's §5, step 8), and a
dated change remedies it before the registration tag. A reference refused for a duplicate key (item 2) is refused so.

**Can a verdict depend on it?** Yes: the arm, and so its request.

**Does it make a pass easier, or soften a fail?** No pass: the arm is at best inconclusive. It would leave unseen a fail
of that arm's entries that rest on the run's own rows alone, should C0 refuse a reference at judgement; the dry run's
remedy before any run is what keeps that from arising. **Not taken:** judging those entries all the same, which would
open an arm's tables against a reference that C0 has refused.
