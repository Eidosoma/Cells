# Amendment 2, 24 November 2026: the lead's layout rulings (provenance, extra keys, precision)

**These are the lead's rulings on the references agent's layout questions (Q5 to Q7), written into
the spec** so that the judge's reader and the checker are built from this folder alone. They come
before the references' tag.
- **Bands.** None changes. Every criterion, tolerance, accuracy requirement and plant of
  CRITERIA.md stands, as amended by amendment 1.
- **Precedence.** Where this amendment and the earlier files of this folder differ, this amendment
  governs.

## Q5. Provenance

- **Run times live in a sidecar.**
  - Each reference file's `method.run_time_s` holds the sidecar's path, `"out/run_times.json"`,
    not a time.
  - The sidecar records the run times. It is excluded from the bitwise check, since times differ
    between regenerations.
- **Hashes and seeds live in their own records.**
  - The output files' sha256 go in `out/SHA256SUMS`, one line per file in `sha256sum`'s format.
  - The `PYTHONHASHSEED` values checked go in `out/provenance.json`, together with the platform
    (Q7).
  - Both record the bitwise check and are written after it.
  - The bitwise check covers every `reference_*.json` file, the invented one included.
- **What moves out of the files.**
  - README's "record the seeds and each file's sha256 in the files' provenance" now reads: in
    `out/provenance.json` and `out/SHA256SUMS`.
  - SPEC.md §7's sample key `hash_seeds_checked` is no longer required in each file. If present,
    the reader ignores it (Q6).
- **Each JSON file carries `"sha256_of_this_file_excluded": true`,** as SPEC.md §7's sample shows.

## Q6. Extra keys

- **Plant entries may carry extra keys:**
  - `scale` on every plant entry: the s_y its `relative_distance` divides by;
  - on P1′, `route2_bound` and `distance_in_route2_bounds`: route 2's bound, and P1′'s distance in
    units of it (SPEC.md §6).
- **The judge's reader:**
  - it requires every registered key: SPEC.md §7's, with amendment 1's `route2` entries and its
    survival entries;
  - it ignores keys it does not know.

  A missing registered key is a fault (CRITERIA.md C0). An extra key is not.

## Q7. Precision

- **The integration** runs in numpy's long double, x86 extended precision with a 64-bit mantissa.
- **The 50-digit arithmetic.** The closed form (SPEC.md §3, item 8) and the quadrature coefficients
  use the standard library's `decimal` at 50 digits.
- **The accuracy check** is an independent second route.
  - Each published value's `accuracy` is its difference from that route, together with the primary
    route's own refinement where it has one (a 100-times-tighter tolerance, or for a fixed-step
    method a refined step), times the stated safety factor of at least 2 (SPEC.md §3).
  - The requirement for judged values, accuracy ≤ 10⁻¹¹ s_y, is unchanged.
- **The platform is recorded** in `out/provenance.json`: the machine, the operating system, the
  Python and library versions, and numpy's long-double format. Long double is the same bits only on
  one platform, so the bitwise check holds on the recorded platform.
- **Publication is unchanged** (SPEC.md §7).
  - Each value is written as the nearest float64 of its long-double result, as a Python float with
    `repr`.
  - That final rounding, at most half a unit in the last place of a double, is part of its stated
    accuracy.
