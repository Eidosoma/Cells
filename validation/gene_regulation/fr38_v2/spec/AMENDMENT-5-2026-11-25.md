## 2. What governs a shape

1. The tables' own keys and types, as §3 pins them and the sample's README lists them.
2. Amendment 4 §8 for everything §3 does not change.
3. A key the judge needs that neither states is requested through the lead and added by a dated
   amendment, never taken from the other side's code (amendment 4, item 8).

**Matching is by name, never by position.** Entries are matched by `id`, `law`, `route_id`,
`reaction_id`, `membrane_id`, `compartment_id` or, for `route2` and `survival`, by their `fate`,
`ts_s` (and `t2_s`). The types are those the sample's README lists, leaf by leaf. Where it says float,
the reader accepts any JSON number; where it says integer, only an integer.

## 3. The shapes the sample pins

**Item 1. `plants` is a top-level key.** It maps each plant's name to its entry: `P2`, `P5` and `P7`
in AF; `P3a`, `P3b` and `P4 AN` in AN; `P4 B` in B; `P8` and `P8 blank` in C; `P9` in D. "At rung
0.5" in amendment 4 §8.4 means the step the plants ran at (h). It does not nest them under
`rungs["0.5"]`. A plant whose value is null is a missing record: it is unscorable (amendment 4, item
7), never "not caught". In the retry tables `plants` is an empty object, since plants run only at h,
with the honest tolerance at h.

**Item 2. The excess over the blank, and the blank's name.**
- `excess_over_blank` is an object with the two keys `durable` and `short_lived`, each a list with
  one value per output (the length of the run's `t`).
- The matched blank's name is the run entry's own `blank`, a string (in AN, `p_sched held` names
  `blank returned`, the family's one blank; in AF each machine's runs name that machine's blank).
- `blank` is null on a blank, on every run of B, and on every plant except P8, whose `blank` is
  `"P8 blank"`: that blank is the entry of that name in `plants`, not a rung's run. P8's
  `excess_over_blank` is formed against it (amendment 1, item 4).
- A twin, the restart and P8 carry `excess_over_blank` with their blank's name; the reference has no
  counterpart for a twin or the restart, so theirs is compared only as amendment 4, item 7 states.

**Item 4. Extra keys are permitted, and recorded but never judged.**
- In `route2`'s entries: `fate`, `ts_s` and `k_per_s`, beside `value` and `grid_error`. `fate` and
  `ts_s` are read to match the entry to its reference; `k_per_s` is recorded, and a value that departs
  from the definition's k_f by more than 10⁻¹² relative is flagged.
- In `survival`'s entries: `fate`, `t2_s` and `ts_s`, beside `alive_t2`, `alive_ts` and `ratio`.
- `blank` on every entry but a refused one. `host_patch` on the plants, null but on P9's.
- engine_run's other exports in `readouts` (for example `H_route_*`, `int_D_route_*`, `H_total`,
  `H_routes_sum`, `n_tx_release_*`, `label_H_*`; `n_K` and `n_Y` in D; `W_network` in C).
- A blank carries `route2` and `survival` entries (all its survival ratios null). The reference's blank
  carries `series` and `checks` only, so these two are recorded, never judged, and their absence is no
  fault.
- The entries a labelled run carries, and those a blank, a twin, B's run, the restart, a plant and P8
  carry, are the sample README's lists.

**Item 5. Restart, refused entries, provenance and the hash files.**
- **`restart`** appears in AN's table only, as a full run entry with `checkpoint`. It is absent, not
  null, from the other tables and from the retry's. A `restart` that is null or absent in AN's table is
  a missing registered run, and refused. §4 (b) rules a `restart` elsewhere.
- **A refused entry** has exactly four keys: `refused` (true), `refusal` (a string), `definition` and
  `record`. It has no `t`, `readouts`, `source`, `steps` or `record_sha256`. The provenance rule of
  amendment 4, item 6 applies to entries with readouts: a refused entry is its own record, it can never
  pass, and it leaves its arm at best inconclusive (CRITERIA.md §4). The checker confirms it against
  the run's own record and log.
- **`source`** has the four keys `engine_revision` (a string), `checkout_dirty` (a boolean), `snapshot`
  (a string) and `snapshot_patch_sha256` (a string). C0 refuses an entry that lacks any of them, has
  another type for one, or has `checkout_dirty` true: the protocol (step 7) runs from a clean frozen
  snapshot. The judge records all four and flags entries that differ in `engine_revision` or `snapshot`
  from one another, or whose `snapshot_patch_sha256` is not the SHA-256 of an empty file.
- **`record_sha256`** is a string of 64 hexadecimal digits, and **`record`** a string, the record's
  path (cut in the sample, as written in the real table). The judge opens no record: the record file's
  own hash is the checker's to verify.
- **`SHA256SUMS`** has one line per table file: the SHA-256, two spaces, the file's name in that folder.
  A table folder's `SHA256SUMS` covers its table files; `record_sha256` covers the records.

## 4. The judge's four open choices, ruled

- **(a) A table whose SHA-256 departs from `SHA256SUMS`, or is missing from it, is refused: confirmed.**
  It is C0: every run of a refused table is refused, so its arm is at best inconclusive.
  - A departing hash, or a listed table that is missing from the folder, means the export changed or
    was lost after it was hashed.
  - An absent `SHA256SUMS` file is amendment 4, item 6's missing index: recorded and flagged to the
    checker, never refused by itself.
  - A malformed line makes the table it should name missing from the list.
- **(b) A `restart` entry in any table but AN's is ignored and recorded: confirmed.** Only AN has a
  restart (CRITERIA.md §1); a stray one is an extra key (amendment 2, Q6). The same holds for AN's
  retry table.
- **(c) A restart without `checkpoint` is refused: confirmed,** with one exception: a restart that is
  itself a refused entry needs no `checkpoint`. It is scored refused, and AN is then at best
  inconclusive.
- **(d) S comes from the registered grid, and the export's `steps` is recorded and flagged when it
  differs: confirmed.**
  - S is the registered horizon over the rung's step: 14,400 s for A, C and D, 21,600 s for B, at each
    rung that runs, the retry's included.
  - A differing `steps` is not refused by itself; C0's echo of `execution.dt` and `experiment.end_time`
    decides.

Can a verdict depend on any of them? Yes: each turns a run or an arm into refused or inconclusive. None
of them can turn a fail into a pass.

## 5. The reader's check on the sample, before the judge's tag

**The judge's reader must parse the registered sample, as a check it passes and reports.**
- **It recomputes the nine hashes** of §1 and stops if any differs.
- **It reads the six table files** (`table/` AF, AN, B, C and D, and `table-retry/` C) with the same
  code that will read the registered tables, in a mode that checks structure only: keys, nesting and
  types to the leaf, as §3 and the sample's README state them. It takes no number, makes no echo check
  and enforces no registered list length (item 8).
- **It must find no structural fault.** A fault in a value is expected and not checked.
- **It must cover every kind of entry the sample holds:** a labelled run, a blank, a twin, a B run, a
  restart with `checkpoint`, plants (P8 and P8 blank among them), and a refused entry (in D, the
  `p_sched returned unlabelled` run at `"2.0"`).
- **Its report,** in the judge's record beside its tag: the hashes recomputed; the files parsed; the
  entry kinds and run names found, per family; and any unexpected or missing key, or type departure,
  named by path.
- **A check that fails stops the tag,** and the difference goes through the lead to the builder or into
  a dated amendment.

## 6. The sample's values never enter a judgement

- The judge's scoring reads only the registered tables of the campaign, whose hashes the lead records
  at the protocol's step 8.
- A table whose SHA-256 is one of §1's is refused in judgement, and can be read only by the check of
  §5.
- No tolerance, scale, reference, plant distance or verdict may depend on any number in the sample.

## 7. Whether to commit the sample

- **Recommendation: the registered hashes are enough for the tables; commit none of them.**
  - The 5.7 MB of scrubbed tables is under the 20 MB limit for a committed set (the references set
    already stands at it), but a public repository's history keeps it for good, and the README lists
    every key and type to the leaf.
  - The folder is frozen evidence, which AGENTS.md puts under `/mnt/workspaces/Cells`.
  - The judge, the builder and the checker may read it where it is. The lead keeps it unchanged until
    the comparison's record is closed.
- **If the repository must hold the key lists without that folder,** commit the sample's README alone
  (57 KB, its hash is §1's), as `validation/gene_regulation/fr38_v2/format_sample/README.md`: beside the
  spec folder, not inside it, because the references agent reads `spec/` alone.
